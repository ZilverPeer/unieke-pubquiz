# Logbook: spec #1, wave 1 (2026-09-05)

Purpose: a factual record of how each orchestration session went, so the process can be evaluated at the end of the spec. One file per session or wave. Record what was dispatched, what review found, what was sent back, and friction. Keep opinions in the "Observations" section so the facts stay separable from the judgement.

## Session summary

- Orchestrator: main session (Fable). Implementers and reviewers: Sonnet subagents.
- Tickets dispatched in parallel: #2 foundation, #3 schema and seed, #4 announcements. Each on its own branch in its own git worktree (`../Pubquiz-wt-<n>`).
- Result: PRs #12 (#4), #13 (#2), #14 (#3) merged to master in that order. Issues #2, #3, #4 closed. Master green: typecheck and 12 tests.
- Wall-clock per implementer, first pass: #4 about 7 min, #2 about 11 min, #3 about 16 min plus a Docker restart stall. Reviews took 0.5 to 2 min per axis. Fix rounds took 1.5 to 4 min.

## Per ticket

### #4 Announcements (PR #12)

- Dispatch brief fixed: output path and naming, MP3 format, loudness target, voice preference (Edge neural via `msedge-tts`), ffprobe-based verify step, package.json edit budget.
- Implementer delivered in one pass. No fallback voice needed.
- Review, Standards axis: clean. Minor smells in the script (duplicated ffprobe helpers, loose constants), not actioned.
- Review, Spec axis: files run 0.8 to 1.1 s against a spec of "about one to two seconds" (accepted: single spoken word). Measured loudness sat 0.5 to 1.5 LU below the -16 LUFS target while the README claimed precision, and verify never checked loudness.
- Sent back: correct the README claim; add a loudness assertion to verify (tolerance ±2 LU). Fixed in one round. Merged.
- No tdd loop: there is no unit-test seam for a one-off asset generator. Verification was ffprobe plus loudnorm measurement.

### #2 Foundation (PR #13)

- Dispatch brief fixed: module folders and import rules, exact domain type names, three tdd seams (message lookup, PDF shell smoke, fixture builder), no sampling behaviour.
- Implementer followed the tdd loop on the three seams and reported all checks green, but noted it had run `next build` to make typecheck pass.
- Review, Standards axis: clean. No locale branching, no cross-module imports, vocabulary matches CONTEXT.md.
- Review, Spec axis: reproduced a fresh clone and found `npm run typecheck` fails without generated Next.js types. Real acceptance-criterion failure the implementer had noticed and reported but not fixed. Also noted `Composition` is typed as nested arrays rather than a fixed 8x10 shape (accepted, sampling enforces at runtime) and fixture category names are not per Locale (accepted, not needed by sampling tests).
- Sent back: make the typecheck script run `next typegen` first; verify on a fresh clone. Fixed in one round.
- Merge conflict with master in package.json and the lockfile after #12 landed. Resolved by the orchestrator by keeping both sides and re-running `npm install`. Merged.

### #3 Schema and seed (PR #14)

- Dispatch brief fixed: table list from the spec, index rules, RLS with no policies, buckets seeded via `config.toml` `objects_path`, seed thresholds per Locale and Difficulty, one-Locale-only exception items, generated types path, npm scripts.
- Friction: Docker restarted mid-run and the agent parked itself; resumed after a nudge. The host's Hyper-V port reservations covered the committed Supabase ports, so the agent verified with a temporary +10000 port shift and restored `config.toml` before committing.
- Review, Standards axis: one hard finding. CONTEXT.md still listed `text_item_details`, which the spec and migrations deliberately omit. Also `items.updated_at` had no trigger. Judgement calls on timestamps consistency and repeated seed blocks, not actioned.
- Review, Spec axis: clean. Noted two small additions beyond the literal ask (a `(kind, difficulty)` index and bucket rows in a migration for hosted parity), both accepted.
- Sent back: fix the CONTEXT.md bullet; add a moddatetime trigger. Fixed in one round. Merged.
- No tdd loop: the ticket is SQL and seed data. Verification was `db reset`, the coverage query, RLS and constraint probes.

## Friction log

- Package.json and lockfile conflicts between every pair of parallel PRs. Predictable when three tickets each add dependencies and scripts. Cost: one manual resolution per later PR.
- Windows Hyper-V reserves blocks inside the dynamic port range (49152 to 65535). Today's block 55298 to 55397 covered the committed 55320 to 55329. Any port in that dynamic range can be taken after a reboot. Resolved the same day by moving the stack to 45320-45329, below the dynamic range.
- Docker Desktop restarted once during #3, stalling the agent until resumed.
- Implementers self-report green even when they had to do something unusual to get there (#2 ran `next build`). The fresh-clone check in review caught it; the self-report alone would not have.
- Only one local Supabase stack can run at a time, so tickets that touch the database cannot overlap.

## Observations (judgement)

- What went well: fixed file layouts per ticket prevented all source conflicts; pre-agreed seams kept #2's tests small and meaningful; the two-axis review found one real defect per PR that the implementer's own checks had missed; fix rounds via SendMessage to the same agent were fast because it kept its context.
- What to change for wave 2: have implementers merge master before opening the PR to absorb dependency conflicts themselves; require the Spec reviewer to reproduce the acceptance criteria empirically wherever possible, as the fresh-clone check did; schedule #6 and #11 so they never share the Supabase stack; the Supabase ports now sit below 49152 so Hyper-V cannot reserve them.
- Open question for the retrospective: is a full two-axis review worth it on asset-only or SQL-only tickets, or should those get a lighter empirical check?
