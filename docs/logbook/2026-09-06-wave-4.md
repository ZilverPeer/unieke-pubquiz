## Friction log

- Erik asked whether four agents were needed. #24 and #25 are a few lines each and should have been one batched PR with a single empirical review; the playbook only said when to split tickets, not when to merge them. Playbook amended (small-change path); this wave keeps the four agents but reviews #24 and #25 with one empirical reviewer each.

- #27 needed three fix rounds. Round 1 was a brief problem: the ticket said "pick what fits" and the implementer picked the grid that fit the tests, not a hand. The brief should have stated the minimum row pitch (about 25pt) as an acceptance criterion. Rounds 2 and 3 were both long-heading edge cases found only by rasterising; each fix exposed the next. A single "render the worst-case name and look at it" step in the implementer brief would have collapsed them into the first pass.
- The Spec reviewer for #26 reported a right-edge clipping that came from samples generated before the implementer merged master. Reviewers must regenerate from the branch tip, never inspect files an implementer left behind; the orchestrator's own visual check had the same flaw.

## Observations (judgement)

- Playbook effect: #26 took 33 minutes and #27 47 minutes dispatch to merge, against 70 minutes for #11 with more code. No `next build`, no db:reset, one stack start and one stop for the whole wave. The verification budget worked.
- Visual tickets need a visual acceptance criterion in numbers (row pitch, minimum image height, margins), not "pick what fits". Text-extraction tests pass while the page is unusable. Add to the brief template: for renderer tickets, the implementer rasterises the worst-case fixture and includes the PNG paths in the report.
- Forwarding the orchestrator's HARD visual finding immediately, before the reviews finished, saved about 10 minutes on #27.
