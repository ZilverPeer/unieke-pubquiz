Sampling: turns a `QuizRequest` plus an in-memory Item pool into a `Composition` (or a `GenerationFailure`), applying the no-repeat, Category, Difficulty, and no-duplicate-Subsubcategory rules. Pure, no I/O. May import only `src/domain`. Must never import `src/repository` or `src/render`.

## Behaviour

- **Categories**: `categoryPicks` is the customer's Category ids, in pick order, 0 to 8 entries, distinct. With k picks (k >= 1), slot i gets pick `i % k` - so the picks cycle evenly over the 8 slots in pick order (4 picks give 2 slots each, 3 picks give 3/3/2, 1 pick fills all 8). With 0 picks, every slot gets a random Category, distinct across slots; the random source chooses which. More than 8 picks, or a duplicate Category among the picks, throws (invalid input, not a `GenerationFailure`). If the pool doesn't have 8 distinct Categories to give (only reachable with 0 picks), that is a content shortfall, not a caller error: it returns a `GenerationFailure` for the first such slot, with `categoryId: null` and `shortfall` set to how many slots from that one onward are left without a Category.
- **Filling a slot**: a single requested Difficulty is a quota of `ITEMS_PER_SLOT` (10) Items of that level; `mixed` Difficulty is a quota of 4/3/3 across easy/medium/hard - which level gets 4 is chosen by the random source. Either way the quota is expanded into one "quota slot" per requested Item and matched to Subsubcategories by an exact maximum bipartite matching (`matching.ts`, Kuhn's algorithm): a quota slot of Difficulty `d` has an edge to every Subsubcategory with at least one eligible Item of Difficulty `d`, and the matching assigns each quota slot to a distinct Subsubcategory wherever possible, honouring the no-shared-Subsubcategory rule across the whole slot (all three Difficulty levels combined, for `mixed`). A shortfall is reported only when no full assignment exists at all - not from an unlucky greedy per-Difficulty-level pick order that could exhaust a Subsubcategory a later level needed even though a valid overall assignment existed. `excludedItemIds` and Items without a translation for `request.locale` are never eligible. Final position order within a slot is randomised. Items placed in earlier slots of the same Composition are excluded from later slots (this matters most with a single pick, where all 8 slots share one Category); a later slot that cannot be filled without repeating an already-placed Item is a genuine shortfall for that slot.
- **Failure**: the first slot (in slot order) that can't be filled fails the whole Quiz, returning `{ ok: false, failure: { slotIndex, categoryId, shortfall } }`. `categoryId` is the slot's Category and `shortfall` is how many Items short of 10 it ended up when the slot had a Category but ran out of eligible Items; `categoryId` is `null` and `shortfall` is the count of un-categorised slots from `slotIndex` onward when the pool ran out of distinct Categories before every slot (0-pick request) had one.
- **Determinism**: the same seed (via `createSeededRandom`) always yields the same `Composition` for the same input; a different seed generally yields a different one.

## Coverage and dry runs

Two read-side seams reuse the sampler's own rules so they can never disagree with what `sampleComposition` would actually do:

- **`computeCoverage(pool, excludedItemIds?)`**: one `CoverageCell` per (Category present in the pool) x kind x requested Difficulty (easy, medium, hard, mixed) x Locale - `eligibleItems` (of that kind, Category, Locale, not excluded; for mixed, all three Difficulty levels), `subsubcategories` (distinct Subsubcategories among them), and `fits` (whether a full Round slot of `ITEMS_PER_SLOT` can be filled). `fits` calls `fillSlot` directly rather than re-implementing the matching: a single Difficulty is one call; `mixed` fits only when all three possible placements of the 4/3/3 extra (easy, medium or hard getting 4) have no shortfall, since a real Round may draw any of the three - `fillSlot` takes an optional `quotaExtraIndex` (0/1/2) to drive that deterministically without touching `sampleComposition`'s own random draws. Cells are sorted by categoryId, kind (`SLOT_KINDS` order), Difficulty, then Locale (nl, en). Backs the admin coverage page (spec 4) and the pre-payment feasibility check (spec 5).
- **`dryRunRequest(input)`**: for one `SampleInput`, every slot (not just the first) that would fall short, in slot order - an empty array means the request would generate. Walks the slots exactly like `sampleComposition` (same `resolveSlotCategories`, same growing exclusion set of Items already placed by earlier slots) but continues past a short slot instead of stopping there, adding whatever it could place to the exclusions. For the same input and seed, its first entry equals `sampleComposition`'s failure. When the pool doesn't have enough distinct Categories for every slot (only reachable with 0 picks), the result is a single aggregate entry for every slot from that point onward (`categoryId: null`, `shortfall` the count of such slots) - not one entry per un-categorised slot. Persists nothing.

## Property tests

`sample.property.test.ts` and `matching.property.test.ts` use `fast-check` over generated pools, requests and seeds (fixed global seed, 100 runs each) to check: no duplicate/excluded/wrong-Locale Item, every filled slot meets its exact Difficulty quota with no shared Subsubcategory, determinism for a repeated seed, that the pick-count cycle rule lands each pick in `floor(8/k)` or `ceil(8/k)` slots in pick order for every k 0-8 (property 5), and that a reported shortfall is genuine (verified against a brute-force search on small graphs, since fast-check can't shrink to a false-shortfall bug on its own). A within-Composition duplicate check covers both a single pick cycled onto all 8 slots (earlier-slots-excluded tracking, see issue #34) and several distinct picks (each pick's own Category rules out overlap by construction) - both rule out a repeated Item across the whole Composition.
